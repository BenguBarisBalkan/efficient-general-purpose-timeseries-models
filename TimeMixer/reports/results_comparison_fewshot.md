# Few-shot forecasting (10% training data) — SparseTSF and TimeMixer

Each model is trained on only the **first 10% of the training split** (`run.py --percent 10`);
validation and test splits are untouched, so these numbers sit on the same test sets as the
full-data forecasting tables. `seq_len=96`, `pred_len ∈ {96,192,336,720}`, MSE/MAE. Generated by
`benchmarks/run_fewshot_benchmarks.py` (idempotent).

- SparseTSF config = its published forecasting setup (`lr=0.02`, 30 epochs, `lradj=type3`,
  `model_type=linear`), `period_len` 24 for hourly (ETTh, Electricity) and 4 for ETTm/Weather.
- TimeMixer config = its own long-term configuration per dataset (`benchmarks/tm_config.py`: the
  learning rate, epochs and patience of the full-data runs).
- Both models train at **batch 32** (see below), the one shared change for the few-shot protocol.
- The few-shot subsetting keeps the *scaler* fit on the full training range (matches the
  Time-Series-Library convention), so only the number of training samples changes.
- **SparseTSF and TimeMixer are both run locally**, same machine and same protocol. The *published*
  TimeMixer / TimeMixer++ columns (TimeMixer++ paper, ICLR'25, Table 5) are in italics.
- **Read the local TimeMixer ETT figure with care.** It is 0.513 against its published 0.453, the
  one task where the local TimeMixer falls clearly short of its paper. Batch 32 with the learning
  rate tuned for full-data batch 128 likely does not suit it. SparseTSF beats both figures on ETT
  (0.441), but the margin against the published one is a modest ~3%.

## Batch size: why 32, not SparseTSF's published 256

With only 10% of the training split **and** `drop_last=True`, the long-horizon ETTh configs produce
~135 training windows — which is **0 batches** at `batch_size=256`, so those runs died with
`Expected positive integer steps_per_epoch, but got 0`. Since the 720-horizon configs are the
hardest, silently losing them biased the ETT average *downwards*. Every config in this table was
therefore re-run at `batch_size=32`, which keeps all of them non-empty and keeps the table on a
single consistent protocol.

## Electricity @ pred_len=720: measured with streaming metrics

This cell used to exhaust RAM on this 16 GB machine. Not the model but the *evaluation* step:
`exp_long_term_forecasting.test()` materialises the full prediction and ground-truth tensors
(`4541 × 720 × 321` float32 ≈ **4.2 GB each**, ~12.6 GB with the stacking step).

Both models now run it with `--stream_metrics 1`, which accumulates the same metric sums batch by
batch instead of storing every prediction. Checked against the default path on ETTh1 and PEMS08, it
agrees to 6–7 significant digits. Only the Electricity-720 cells use it, so the Electricity averages
cover all four horizons like the published ones.
