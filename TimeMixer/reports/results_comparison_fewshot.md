# Few-shot forecasting (10% training data) — SparseTSF

Each model is trained on only the **first 10% of the training split** (`run.py --percent 10`);
validation and test splits are untouched, so these numbers sit on the same test sets as the
full-data forecasting tables. `seq_len=96`, `pred_len ∈ {96,192,336,720}`, MSE/MAE. Generated by
`benchmarks/run_fewshot_benchmarks.py` (idempotent).

- SparseTSF config = its published forecasting setup (`lr=0.02`, batch 256, 30 epochs,
  `lradj=type3`, `model_type=linear`), `period_len` 24 for hourly (ETTh, Electricity) and 4 for
  ETTm/Weather.
- The few-shot subsetting keeps the *scaler* fit on the full training range (matches the
  Time-Series-Library convention), so only the number of training samples changes.
- **Only SparseTSF is run locally.** TimeMixer / TimeMixer++ columns are the *published* values
  from the TimeMixer++ paper (ICLR'25, Table 5), in italics — not re-run here and tuned by their
  authors, so they are a reference point, not a like-for-like comparison.

## Batch size: why 32, not SparseTSF's published 256

With only 10% of the training split **and** `drop_last=True`, the long-horizon ETTh configs produce
~135 training windows — which is **0 batches** at `batch_size=256`, so those runs died with
`Expected positive integer steps_per_epoch, but got 0`. Since the 720-horizon configs are the
hardest, silently losing them biased the ETT average *downwards*. Every config in this table was
therefore re-run at `batch_size=32`, which keeps all of them non-empty and keeps the table on a
single consistent protocol.

## Known gap: Electricity @ pred_len=720

That single cell is **not measured** — it exhausts RAM on this 16 GB machine, not because of the
model but because of the *evaluation* step. `exp_long_term_forecasting.test()` materialises the full
prediction and ground-truth tensors before computing metrics: `4541 × 720 × 321` float32 ≈ **4.2 GB
each**, and the stacking step needs the batch list and the output array alive simultaneously
(~12.6 GB in total, plus PyTorch/CUDA overhead).

The stacking was already changed from `np.concatenate` to an incremental copy that frees each batch
as it is consumed (`_stack()` in that file — verified bit-identical, roughly half the previous peak),
which is what makes `pred_len` 96/192/336 succeed. 720 remains out of reach.

**The Electricity row in the averages above is therefore over 3 of 4 horizons** and is not
strictly comparable to the published 4-horizon average. Making it measurable would require computing
the metrics in a streaming fashion (accumulating per-batch sums instead of storing every prediction)
— exact for MSE/MAE, but a change to shared evaluation code that would want its own verification.
